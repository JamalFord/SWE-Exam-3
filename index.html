1. SDLC, 4 P's & Ethics
• SDLC: Req → Design → Impl → Test → Deploy → Maint.
• 4 P's: People, Product, Process, Project.
• 4 Attributes: Maintainability, Dependability/Security, Efficiency, Acceptability.
• Cost: 60% Dev, 40% Test. Evolution cost > Dev cost for custom software.
• Ethics (ACM/IEEE): Public > Client/Employer > Product > Judgment > Management > Profession > Colleagues > Self.
2. Kruchten 4+1 View Model
• Logical View: End-user functionality, classes, domain models. (Audience: Devs/Users)
• Process View: Concurrency, threads, runtime performance, scalability. (Audience: Devs)
• Development View: Code artifacts, packages, modules, build hierarchy. (Audience: Devs)
• Physical View: Hardware nodes, networks, servers, deployment. (Audience: Ops)
• +1 Scenarios (Use Cases): Unifies & links all 4 views together!
3. Architecture Decisions
• IEEE Def: "Fundamental organization embodied in components, relationships to one another/environment, principles of design & evolution."
• Partitioning 3 steps: 1. System Structuring, 2. Control Modeling, 3. Modular Decomposition.
• Why Plan? Stakeholder communication, pre-code system analysis, large-scale reuse, security control access.
4. Four Architectural Patterns
• 1. Layered: Functionality split into levels; layer N only calls layer N-1.
  (+) Modular, replaceable layers, security defense-in-depth.
  (-) Hard clean separation; perf overhead through calls.
  Ex: UI → Auth/Forms → Logic → DB.
• 2. Repository (Blackboard): Passive central DB + active tools.
  (+) Efficient large data sharing, tool independence.
  (-) Single point of failure; data schema compromise.
  Ex: IDE (Project Info/Code in center).
• 3. Client-Server: Servers provide services; clients call via network.
  (+) Distributed, scalable, independent upgrades.
  (-) Network latency, each service point of failure.
  Ex: Film Library (Video, Catalogue, Picture servers).
• 4. Pipe & Filter: Sequential data transformations.
  (+) High reuse, easy to add filter, Unix style.
  (-) Agreed data format overhead, latency.
  Ex: Invoice → Process → Payments → Receipts.
5. System Control Models
• Centralized - Call-Return: Top-down subroutine tree for sequential systems (Main → Subsystems → Methods).
• Centralized - Manager: One System Controller starts/stops/coordinates concurrent tasks (Sensors, Actuators, Fault Handler, UI).
• Event - Broadcast: Events sent to message bus; registered subsystems handle. (Decentralized, but uncertain handling time).
• Event - Interrupt-Driven: Memory-mapped hardware interrupt array → handlers. Ultra fast real-time, but hard to validate!
6. Testing V&V & Scaffolding
• Verification: "Are we building the product RIGHT?" (conforms to specification).
• Validation: "Are we building the RIGHT product?" (satisfies user needs).
• Dijkstra's Axiom: "Testing shows the presence of bugs, NEVER their absence!"
• Defect vs Validation: Defect exposes flaws; Validation demonstrates functionality meets requirements.
• Test Scaffolding:
  * Driver: Simulates caller module (invokes unit).
  * Stub/Mock: Simulates called sub-module (dummy return).
  * Harness: Test execution environment (JUnit).
  * Oracle: Compares actual vs expected output.
7. V-Model & JUnit Lifecycle
• V-Model Pairs:
  Req ↔ Acceptance Test (Alpha/Beta)
  System Spec ↔ System Testing
  Arch Design ↔ Subsystem/Integration Testing
  Detailed Design ↔ Unit Testing
• JUnit Annotations:
  @Test: Defines test method.
  @Before / @BeforeEach: Runs before EVERY test.
  @After / @AfterEach: Runs after EVERY test.
  @BeforeClass / @BeforeAll: Runs ONCE before suite (static, e.g. open DB).
  @AfterClass / @AfterAll: Runs ONCE after suite.

9. UML Notations & Visibility
• Visibility: + Public | - Private | # Protected | ~ Package
• Finding: Noun = Class, Noun phrase = Attribute, Verb = Method.
• Association: Solid line --- with multiplicity (1, 0..1, 1..*, *).
• Aggregation <>-- : Open diamond at whole. "has-a", weak ownership. Part outlives whole! E.g. Department <>-- Doctor (doctors retain licenses).
• Composition <*>-- : Solid diamond at whole. "part-of", strong ownership. Part destroyed with whole! E.g. Department <*>-- LabTest, Customer <*>-- Address.
• Generalization --|> : Hollow triangle at parent. "is-a" inheritance. E.g. MedicalRecord --|> SurgicalRecord.
• Realization ..|> : Dashed line with hollow triangle at Interface. E.g. SavingsAccount ..|> InterestBearing.
• Dependency ..> : Dashed line with open arrow ("uses").
10. Sequence Diagram Rules
• Lifeline: Vertical dashed line under object box.
• Activation: Vertical thin rectangle of execution.
• Sync Message: Solid line + filled arrowhead ——▸ (blocking).
• Async Message: Solid line + stick open arrow ——> (non-blocking).
• Return: Dashed line + stick arrow <- - -
• Fragments: alt (if-else separated by dashed line), opt (if only), loop [min, max], par (parallel).
• Creation/Destruction: «create» message points to box; X marks destruction.

  * Fork: 1 incoming → 2+ concurrent flows (thick bar).
  * Join: 2+ concurrent → 1 outgoing flow (thick bar).
  * Final Node: Bullseye (dot in circle).
  * Swimlanes: Partitions showing responsible actors.

12. Structural Testing & Coverage
• Statement Coverage ($C_0$):
  $\frac{\text{statements executed}}{\text{total statements}} \times 100\%$. Weakest! Misses false branches in single if blocks.
• Branch Coverage ($C_1$):
  Every decision edge (True & False) taken ≥ 1.
  Subsumption: Branch subsumes Statement ($C_1 \implies C_0$).
• Condition Coverage: Each individual boolean sub-expression evaluates to T & F at least once.
• MC/DC (Modified Condition/Decision):
  Avionics DO-178C standard. Each condition shown to independently affect decision outcome with other conditions held fixed.
  Test count: $n + 1$ tests (vs $2^n$ multiple condition).
• Path Coverage: Every execution path. Often infinite/intractable due to loops.
• Loop Boundary: 0 iterations, 1 iteration, typical, max-1, max iterations.
13. Black-Box (EP & BVA)
• Equivalence Partitioning (EP): Partition input into valid & invalid classes. Pick 1 test value per class.
• Boundary Value Analysis (BVA): Test edges of ranges ($min-1, min, min+1, nom, max-1, max, max+1$).
• Example PIN [0000..9999]: Valid: 1234; Invalid: -1, 10000, "ABCD", 3-digits, 5-digits.
14. 5 Test Cases Structure
Format: [ID, Objective, Pre-Cond, Steps/Input, Expected Result, Criteria]
• TC-1 (Valid Eq): Normal input → Success HTTP 200/201.
• TC-2 (Min BVA): Input = 0 or min → Valid boundary accepted.
• TC-3 (Negative BVA): Input = min-1 or max+1 → Form blocked, specific error message displayed.
• TC-4 (Concurrency): Simultaneous requests → Balance protected, race condition prevented.
• TC-5 (Exception/Null): Null required field → HTTP 400 Bad Request, graceful error logging (no 500 crash).
15. Database & Normal Forms
• Entity Integrity: Primary Key (PK) cannot be NULL.
• Referential Integrity: Foreign Key (FK) must match existing PK in referenced table or be NULL.
• 1NF: Atomic column values, no repeating groups.
• 2NF: 1NF + no partial functional dependencies (all non-key attributes fully depend on composite PK).
• 3NF: 2NF + no transitive dependencies (no non-key attribute depends on another non-key attribute).
"Each attribute must depend on the key, the whole key, and nothing but the key!"
