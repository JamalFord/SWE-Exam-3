Diagram 6: Insulin Pump Activity Diagram (Fork & Join)

A Fork bar splits 1 incoming flow into multiple concurrent parallel flows. A Join bar synchronizes concurrent parallel flows into 1 outgoing flow.

• Fork: After sensor measures blood sugar, execution splits into: (1) Compute required insulin dosage, and (2) Log sensor timestamp.
• Join: Both the dosage calculation and logging must complete before advancing to Inject Insulin.
• Decision Diamond: [sugarLevel > safeRange] → Inject Insulin; [sugarLevel ≤ safeRange] → Sleep 10 min.

Diagram 9: Use Case Diagram (Include vs Extend)

Differentiating mandatory sub-tasks from optional extension points.

• «include»: Mandatory sub-routine. Base use case is incomplete without it. Dashed arrow points from base use case to included use case. (E.g. View Record --> «include» --> Authenticate User).
• «extend»: Optional behavior triggered under specific conditions at an extension point. Base is complete on its own. Dashed arrow points from extending use case to base use case. (E.g. Print Hardcopy --> «extend» --> View Record).

sdlc & fundamentals: reqs -> design -> code -> test -> deploy -> maint. 4 p's: people, product, process, project. 4 attributes of good software: maintainability (system evolves w/ customer needs), dependability & security (reliable, safe, resilient), efficiency (optimal cpu, memory, response time), acceptability (understandable, usable, compatible). cost breakdown: roughly 60% dev cost, 40% testing cost; for custom software, long-term evolution costs exceed original development! acm/ieee ethics priority: 1.public interest 2.client & employer 3.product 4.judgment 5.management 6.profession 7.colleagues 8.self.
requirements & use cases: functional = services system must provide & reactions to inputs. non-functional (nfr) = constraints on services (timing, security, standards, reliability, portability). testability rule: avoid subjective vague words (instantaneously, user-friendly, rapidly, little training) -> must rewrite into measurable numbers (e.g. response <= 200 ms, training time <= 2 hours, errors <= 1 per 8 hour shift). use cases: <> = mandatory subroutine (base incomplete without it); <> = optional behavior triggered at extension point (base is complete on its own).
kruchten 4+1 view model: logical view = end-user functionality, domain abstractions, classes, entities (audience: dev/user, concern: functional reqs). process view = dynamic runtime behavior, concurrency, processes, threads, synchronization, rpc/message bus (audience: dev, concern: performance & scalability). development view = static organization of code, packages, modules, libraries, build hierarchy (audience: dev, concern: reuse & ease of build). physical view = hardware topology, execution nodes, network interconnects, distribution across processors (audience: sys eng/ops, concern: quality attributes). +1 scenarios (use cases) = unifies and links the other 4 views together, validating architecture against all requirements.
architecture & patterns: ieee definition: fundamental organization of a system embodied in its components, relationships to one another and environment, and principles governing design and evolution. partitioning: 1.system structuring -> 2.control modeling -> 3.modular decomposition. why plan: stakeholder communication, system analysis before code, large-scale reuse, security access boundary enforcement. layered architecture: hierarchical layers where layer n only depends on n-1; pros: replaceable layers if interfaces constant, changes localized to adjacent layers, multi-layer security defense; cons: clean separation hard in practice, performance overhead passing calls through layers. repository: central passive data store accessed and updated by independent active subsystems (example: ide w/ project info and code surrounded by java editor, python editor, code gen, report gen); pros: efficient sharing of large data, independent components; cons: single point of failure and bottleneck, data evolution difficult. client-server: dedicated servers offering services across network to clients (film library: catalogue server, video server, picture server); pros: distributed failure isolation, straightforward scaling; cons: network latency, each server a failure point. pipe & filter: sequential stream transformations (unix pipes, customer invoicing: invoices -> process invoices -> identify payments -> issue receipts); pros: subsystem reuse, intuitive; cons: agreed data format overhead, parsing latency. mvc: controller handles input -> updates model -> view renders display.
system control models: centralized call-return model = top-down subroutine call tree for sequential code (main -> subsystems -> methods). centralized manager model = single process controls stopping, starting, and coordination of concurrent processes (controller coordinating sensors, actuators, computation, fault handler, ui). decentralized broadcast model = events published to common message bus; registered subsystems handle events (effective for distributed systems, but sender does not know if or when event handled). decentralized interrupt-driven model = hardware interrupt array mapped to specific memory locations; dedicated handlers watch address and coordinate response (temperature, radiation, fire alarm, fuel handlers; used for fast real-time response, but complex to program and hard to validate).
software testing fundamentals: verification = "are we building the product right?" (conformance to specification). validation = "are we building the right product?" (satisfies customer operational needs). dijkstra's axiom: "program testing can be used to show the presence of bugs, but never to show their absence!" defect testing exposes flaws; validation testing demonstrates system meets user requirements. v-model lifecycle pairings: requirements engineering <-> acceptance testing (alpha and beta); system specification <-> system testing; architectural design <-> subsystem and integration testing; detailed module design <-> unit testing.
test scaffolding & junit: test driver = software module that invokes unit under test and passes simulated inputs. test stub / mock = dummy module called by unit under test that returns synthetic values. test harness = framework automating execution of test suites (example: junit). test oracle = mechanism determining if actual output matches expected output. junit annotations: @Test = marks executable test method; @Before / @BeforeEach = executes before every individual test method (fixture init); @After / @AfterEach = executes after every test method (fixture teardown); @BeforeClass / @BeforeAll = static, executes once before all tests in class (opens db/sockets); @AfterClass / @AfterAll = static, executes once after all tests finish (closes db/sockets).
mentcare & atm architecture: mentcare 4-layer system: layer 1 is web browser; layer 2 is user communications (login, role checking, form & menu manager, data validation); layer 3 is information retrieval and modification (security management, patient info manager, data import/export, report generation); layer 4 is transaction management and patient database. atm 4-tier pipeline: i/o processing <-> application logic <-> transaction manager <-> database. atm 3-phase flow: input (get account id, validate card, select service) -> process (query account, update account) -> output (print details, return card, dispense cash).
uml class diagrams: strict 3-compartment rule: every class box must show all 3 compartments: 1.class name 2.attributes 3.operations (even if attributes or operations are empty, draw the 3rd compartment box line!). class discovery: nouns become classes, noun phrases become attributes, verbs become operations. abstract class: render name in italic font style or tag with <>. visibility symbols: + is public, - is private, # is protected, - is package-private. attribute format: visibility name : type = default-val. operation format: visibility name(parameter : type) : returnType. association: solid line without arrows or with open navigation arrow; multiplicity placed at both ends (1, 0..1, 1..*, *). aggregation (<>--): open hollow diamond at whole end ("has-a", weak containment, part can exist independently of whole: department <>-- doctor). composition (<*>--): solid filled diamond at whole end ("part-of", strong containment, part lifetime bound to whole; destroyed when whole deleted: department <*>-- labtest, customer <*>-- address). generalization (--/->): solid line with hollow triangular arrowhead pointing to parent ("is-a", inheritance: medicalrecord --/-> surgicalrecord, bankaccount --/-> checkingaccount). realization (../->): dashed line with hollow triangular arrowhead pointing to interface (savingsaccount ../-> interestbearing). dependency (..>): dashed line with open arrow ("uses").
adapter pattern: client calls methods on target interface; target = abstract interface expected by client; adapter = implements target interface (../-> target) and holds private reference to adaptee instance (adapter calls adaptee.specificRequest()); adaptee = existing legacy class with incompatible interface that client cannot call directly.
sequence diagrams: lifeline = vertical dashed line extending downward from object box; activation bar = thin vertical rectangle on lifeline indicating execution control; synchronous call = solid line with filled arrowhead (----->); sender halts until reply; asynchronous call = solid line with stick open arrowhead (--->); sender continues without waiting; reply / return message = dashed line with stick open arrow (<---); object creation = message labeled <> points directly to object box; object destruction = an x placed at base of an activation lifeline. combined fragments: alt = mutually exclusive if-then-else separated by dashed line with [guard]; opt = optional conditional execution if only; loop [min, max] = repetition over elements; par = concurrent parallel sub-sequences.
activity & statechart diagrams: activity elements: initial node = solid filled circle; activity state = rounded rectangle; decision and merge = diamond symbols with [guard]; fork bar = thick black synchronization bar splitting 1 incoming flow into 2 or more concurrent parallel flows; join bar = thick black synchronization bar waiting for multiple concurrent flows to finish before 1 outgoing flow proceeds; final node = bullseye (solid circle inside outer circle); swimlanes (partitions) = indicate which role or subsystem performs each activity. insulin pump flow: sensor measures blood sugar -> fork bar splits into: (1) calculate required insulin dosage, and (2) log sensor reading -> join bar synchronizes both -> decision diamond [sugar > target] -> inject insulin. state machine: states = rounded rectangles (waiting, half power, full power, operation, disabled); initial state = solid black circle; final state = bullseye; transition label syntax: event [guard] / action (example: start [door-closed] / run-generator(300w); door-open / stop-generator(), turn-lamp-on() -> state disabled).
white-box structural testing: statement coverage (c0) = percentage of executable statements traversed by test cases (statements executed / total statements * 100%; weakest metric! cannot detect missing false branches in single if). branch coverage (c1) = requires every decision branch (both true and false edges in control flow graph) traversed at least once. subsumption rule: branch coverage subsumes statement coverage (100% branch implies 100% statement, but not vice-versa!). condition coverage = requires each individual boolean sub-condition in composite expression to evaluate to true and false at least once. mc/dc (modified condition/decision coverage) = required by do-178c avionics safety standard: each condition must be shown to independently affect overall decision outcome while holding all other conditions fixed; for n conditions, requires n + 1 test cases (compared to 2**n for multiple condition coverage). path coverage = every possible execution path from entry to exit tested (often infinite or intractable due to loops). loop boundary = test 0 iterations, 1 iteration, typical iterations, max-1 iterations, max iterations.
black-box testing (ep & bva): equivalence partitioning (ep) = divide input domain into valid and invalid equivalence classes; select 1 representative test input per class. boundary value analysis (bva) = test values immediately at, below, and above boundary edges: min-1, min, min+1, nominal, max-1, max, max+1. pin [0000..9999]: valid class = 1234; invalid classes = negative numbers (-1), numbers > 9999 (10000), non-digits ("abcd"), 3 digits, 5 digits.
5 test cases structure & rubric: format: [tc id, objective, pre-conditions, test steps/inputs, expected result, pass/fail criteria]. tc-01 (valid ep registration): pre: user logged in; inputs: valid name, dob, ssn; expected: patient record created in db, unique id assigned, http 201 toast; criteria: record persists in db. tc-02 (min boundary value): inputs: age = 0 (minimum valid age); expected: form accepted, classified as infant; criteria: profile created with infant tag. tc-03 (negative boundary value): inputs: age = -1; expected: submission blocked, error message "age must be >= 0" displayed; criteria: no db write, form retains input. tc-04 (concurrency / double withdrawal): pre: balance = $100; inputs: simultaneous atm and mobile app withdrawals of $100 within 10 ms; expected: 1st transaction succeeds, 2nd rejected for insufficient funds; criteria: balance never negative ($0 balance). tc-05 (exception / null pointer): inputs: doctorid = null on prescription request; expected: system rejects with http 400 bad request, logs missing doctor reference safely; criteria: no unhandled 500 crash or stack trace shown.
relational database & normalization: entity integrity: primary key (pk) column cannot be null and must be unique. referential integrity: foreign key (fk) column must match an existing valid pk value in parent table or be null. 1nf (first normal form): all column values must be atomic (no repeating groups, multi-valued attributes, or composite values). 2nf (second normal form): table is in 1nf and every non-key attribute is fully functionally dependent on the entire composite primary key (no partial key dependencies). 3nf (third normal form): table is in 2nf and no non-key attribute depends on another non-key attribute (no transitive dependencies). canonical rule: "every attribute must depend on the key, the whole key, and nothing but the key!"
