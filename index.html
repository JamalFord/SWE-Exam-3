Diagram 6: Insulin Pump Activity Diagram (Fork & Join)

Differentiating mandatory sub-tasks from optional extension points.

Handwritten Cheat Sheet (Front & Back)

Pure unbolded handwritten text • No borders, no dashed lines, no headers • Ready for 8.5" x 11" paper

SDLC and Fundamentals:
- SDLC phases: Requirements -> Design -> Implementation -> Testing -> Deployment -> Maintenance.
- 4 Ps of SWE: People, Product, Process, Project.
- 4 software quality attributes: Maintainability (system evolves with changing customer needs), Dependability & Security (reliability, safety, resilience), Efficiency (optimal CPU, memory, responsiveness), Acceptability (understandable, usable, compatible).
- Software costs: roughly 60% development cost, 40% testing cost. For custom software systems, long-term evolution costs exceed original development costs.
- ACM/IEEE professional ethics priority: 1. Public interest, 2. Client and employer, 3. Product, 4. Judgment, 5. Management, 6. Profession, 7. Colleagues, 8. Self.
Requirements Engineering:
- Functional requirements: statements of services system must provide, reactions to inputs, behavior in situations.
- Non-functional requirements (NFR): constraints on services and system functions such as timing, security, standards, reliability.
- Precision rules: avoid vague subjective language. Words like "instantaneously", "user-friendly", "rapidly", "little training" must be rewritten into measurable engineering values (e.g. response time <= 200 ms, training time <= 2 hours, error rate <= 1 error per 8 hour shift).
- Use case relationships: «include» represents a mandatory sub-task where base use case is incomplete without it. «extend» represents an optional behavior triggered at an extension point where base use case is complete on its own.
Kruchten 4+1 View Model:
- Logical View: end-user functionality, domain abstractions, classes, entities. Target audience: developers and users. Concern: functional requirements.
- Process View: dynamic runtime aspects, concurrency, active processes, threads, synchronization, communication (RPC, message bus). Target audience: developers. Concern: performance, scalability.
- Development View: static organization of code artifacts, packages, modules, libraries, build hierarchy. Target audience: developers. Concern: reuse, ease of build.
- Physical View: hardware topology, execution nodes, network interconnects, distribution across processors. Target audience: system engineers and operations.
- +1 Scenarios (Use Cases): unifies and links the other 4 views together, validating that architecture satisfies all requirements.
Architectural Design and Styles:
- IEEE architecture definition: fundamental organization of a system embodied in its components, relationships to one another and environment, and principles governing its design and evolution.
- Partitioning process: 1. System Structuring, 2. Control Modeling, 3. Modular Decomposition.
- Why plan explicitly: stakeholder communication, system analysis before coding, large-scale subsystem reuse, security access boundary enforcement.
- Layered Architecture: system organized into hierarchical layers where layer N only depends on layer N-1. Advantages: replaceable layers if interfaces held constant, changes isolated to adjacent layers, multi-layer security defense. Disadvantages: clean separation difficult in practice, performance overhead passing calls through multiple layers.
- Repository Architecture: central passive data store accessed and updated by independent active subsystems. Example: IDE with central Project Information and Code surrounded by Java Editor, Python Editor, Model Editor, Code Generator, Report Generator, Design Analyzer. Advantages: efficient sharing of large datasets, independent components. Disadvantages: single point of failure and communication bottleneck, data evolution is difficult.
- Client-Server Architecture: set of dedicated servers offering services across network to clients. Example: Film Library with wide-bandwidth network connecting clients to Catalogue Server, Video Server, Picture Server, Hypertext Server. Advantages: distributed failure isolation, straightforward scaling. Disadvantages: network latency, each server is a failure point.
- Pipe and Filter Architecture: sequential stream transformations where output of one filter serves as input to next through pipe (e.g. Unix pipes, invoice processing: Invoices -> Process Invoices -> Identify Payments -> Issue Receipts). Advantages: subsystem reuse, intuitive flow. Disadvantages: agreed data format overhead, high parsing latency.
- MVC: Controller handles input, Model maintains state and logic, View renders display output.
System Control Models:
- Centralized Call-Return Model: top-down subroutine call tree applicable to sequential systems (Main -> Subsystems -> Methods).
- Centralized Manager Model: single process controls stopping, starting, and coordination of concurrent processes (System Controller coordinating Sensors, Actuators, Computation, Fault Handler, User Interface).
- Decentralized Broadcast Model: events published to common message bus; registered subsystems handle events. Effective for distributed systems, but subsystems do not know if or when event handled.
- Decentralized Interrupt-Driven Model: hardware interrupt array mapped to specific memory locations; dedicated handlers watch address and coordinate response (e.g. Temperature, Radiation, Fire Alarm, Fuel handlers). Used for fast real-time response, but complex to program and hard to validate.
Software Testing Fundamentals:
- Verification: "Are we building the product right?" (conformance to specification).
- Validation: "Are we building the right product?" (satisfies customer operational needs).
- Dijkstra's axiom: "Program testing can be used to show the presence of bugs, but never to show their absence."
- Defect testing exposes flaws; validation testing demonstrates system meets user requirements.
- V-Model lifecycle pairings:
Requirements engineering <-> Acceptance testing (alpha and beta)
System specification <-> System testing
Architectural design <-> Subsystem and integration testing
Detailed module design <-> Unit testing
Test Scaffolding and JUnit:
- Test Driver: software module that invokes the unit under test and passes simulated inputs.
- Test Stub / Mock: dummy module called by the unit under test that returns synthetic values.
- Test Harness: framework environment that automates execution of test suites (e.g. JUnit).
- Test Oracle: mechanism (specification, human, dual run) determining if actual output matches expected output.
- JUnit annotations:
@Test: marks executable test method.
@Before / @BeforeEach: executes before every individual test method to initialize test fixture.
@After / @AfterEach: executes after every test method to tear down test fixture.
@BeforeClass / @BeforeAll: executes once before all test methods in class (static, opens DB/sockets).
@AfterClass / @AfterAll: executes once after all test methods finish (static, closes DB/sockets).

UML Class Diagram Syntax and Rules:
- Strict 3-compartment rule: every class box must show all 3 compartments: 1. Class Name, 2. Attributes, 3. Operations. Even if attributes or operations are empty, draw the 3rd compartment box line.
- Class discovery: Nouns become Classes, Noun phrases become Attributes, Verbs become Operations.
- Abstract class name: render in italic font style or tag with «abstract».
- Visibility symbols: + is Public, - is Private, # is Protected, ~ is Package-private.
- Attribute format: visibility name : type = defaultValue.
- Operation format: visibility name(parameter : type) : returnType.
- Association: solid line without arrows or with open navigation arrow; multiplicity placed at both ends (1, 0..1, 1..*, *).
- Aggregation (<>--): open hollow diamond at whole end. Represents weak containment ("has-a"). Part can exist independently of whole. Doctor outlives Department (Department <>-- Doctor).
- Composition (<*>--): solid filled diamond at whole end. Represents strong containment ("part-of"). Part lifetime bound to whole; destroyed when whole is deleted. Department <*>-- LabTest, Customer <*>-- Address.
- Generalization (--|>): solid line with hollow triangular arrowhead pointing to parent class. Represents inheritance ("is-a"). MedicalRecord --|> SurgicalRecord, BankAccount --|> CheckingAccount.
- Realization (..|>): dashed line with hollow triangular arrowhead pointing to interface. SavingsAccount ..|> InterestBearing.
- Dependency (..>): dashed line with open arrow ("uses").
Adapter Pattern Class Diagram:
- Client: calls methods on the Target interface.
- Target: abstract interface expected by client.
- Adapter: implements Target interface (..|> Target) and holds a private reference to the Adaptee instance (adapter calls adaptee.specificRequest()).
- Adaptee: existing legacy class with incompatible interface that client cannot call directly.
Sequence Diagram Rules:
- Lifeline: vertical dashed line extending downward from object box.
- Activation bar: thin vertical rectangle on lifeline indicating execution control.
- Synchronous call: solid line with filled arrowhead (──▶); sender halts until reply.
- Asynchronous call: solid line with stick open arrowhead (──>); sender continues without waiting.
- Reply / Return message: dashed line with stick open arrow (< - - -).
- Object creation: message labeled «create» points directly to object box.
- Object destruction: an X placed at the base of an activation lifeline.
- Combined fragments: alt (mutually exclusive if-then-else separated by dashed line with [guard]), opt (optional conditional execution if only), loop [min, max] (repetition over elements), par (concurrent parallel sub-sequences).
Activity and Statechart Diagrams:
- Activity Diagram elements: initial node is solid filled circle; activity state is rounded rectangle; decision and merge are diamond symbols with [guard]; fork bar is thick black synchronization bar splitting 1 incoming flow into 2 or more concurrent parallel flows; join bar is thick black synchronization bar waiting for multiple concurrent flows to finish before 1 outgoing flow proceeds; activity final node is bullseye (solid circle inside outer circle); swimlanes (partitions) indicate which role or subsystem performs each activity.
- Insulin pump activity flow: sensor measures blood sugar -> fork bar splits into: (1) calculate required insulin dosage, and (2) log sensor reading -> join bar synchronizes both -> decision diamond [sugar > target] -> inject insulin.
- State Machine diagram: states shown as rounded rectangles (Waiting, Half power, Full power, Operation, Disabled); initial state is solid black circle; final state is bullseye.
- Transition label syntax: Event [Guard] / Action.
- Microwave example: start [door_closed] / run_generator(300W); door_open / stop_generator(), turn_lamp_on() -> state Disabled.
White-Box Structural Testing and Coverage:
- Statement Coverage (C0): percentage of executable statements traversed by test cases (statements executed / total statements * 100%). Weakest coverage metric! Cannot detect missing false branches in single if statements.
- Branch Coverage (C1): requires every decision branch (both True and False edges in Control Flow Graph) to be traversed at least once.
- Subsumption rule: Branch coverage subsumes Statement coverage (100% branch implies 100% statement, but not vice-versa).
- Condition Coverage: requires each individual boolean sub-condition in composite expression to evaluate to True and False at least once.
- MC/DC (Modified Condition/Decision Coverage): required by DO-178C avionics safety standard. Each condition must be shown to independently affect the overall decision outcome while holding all other conditions fixed. For n conditions, requires n + 1 test cases (compared to 2^n for multiple condition coverage).
- Path Coverage: every possible execution path from entry to exit tested. Often infinite or intractable due to loops.
- Loop Boundary Coverage: test 0 iterations, 1 iteration, typical iterations, max-1 iterations, max iterations.
Black-Box Testing (EP & BVA):
- Equivalence Partitioning (EP): divide input domain into valid and invalid equivalence classes; select 1 representative test input per class.
- Boundary Value Analysis (BVA): test values immediately at, below, and above boundary edges: min-1, min, min+1, nominal, max-1, max, max+1.
- PIN [0000..9999]: valid class = 1234; invalid classes = negative numbers (-1), numbers > 9999 (10000), non-digits ("ABCD"), 3 digits, 5 digits.

Relational Database and Normalization:
- Entity Integrity: Primary Key (PK) column cannot be NULL and must be unique.
- Referential Integrity: Foreign Key (FK) column must match an existing valid PK value in parent table or be NULL.
- 1NF (First Normal Form): all column values must be atomic (no repeating groups, multi-valued attributes, or composite values).
- 2NF (Second Normal Form): table is in 1NF AND every non-key attribute is fully functionally dependent on the entire composite Primary Key (no partial key dependencies).
- 3NF (Third Normal Form): table is in 2NF AND no non-key attribute depends on another non-key attribute (no transitive dependencies).
- Canonical rule: "Every attribute must depend on the key, the whole key, and nothing but the key."
