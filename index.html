Diagram 4: Doctor Viewing Record Sequence Diagram (Fragments: Alt & Loop)

Doctor queries patient surgical record. If authorized (`[isAuthorized]`), loop over lab tests and return results; else return error.

Combined Fragment Matching:

alt fragment: Represents if-then-else alternatives. Separated by a dashed horizontal line with boolean guards in square brackets [authorized] and [else].
loop fragment: Represents repeated execution (e.g. iterating over test records) with guard condition [hasMoreTests] or range [1, *].
Arrowhead Types: Synchronous calls use a solid line with filled arrowhead (——▸). Return messages use a dashed line with stick arrowhead (<- - -).

Diagram 6: Insulin Pump Activity Diagram (Fork & Join)

Diagram 9: Use Case Diagram (Include vs Extend)

Differentiating mandatory sub-tasks from optional extension points.

SWE Exam 3 Study Notes • Side 1: Architecture, SDLC & Testing CSC 4350 / 6350 • Fall 2026
SDLC & Fundamentals
• SDLC stages: Requirements → Design → Implementation → Testing → Deployment → Maintenance.
• 4 P's of SWE: People, Product, Process, Project.
• 4 Good SW Attributes: Maintainability (evolves), Dependability & Security (safe), Efficiency (fast, low RAM), Acceptability (usable).
• Costs: 60% Dev, 40% Testing. For custom systems, evolution > initial dev cost.
• ACM/IEEE Ethics Priority: Public interest > Client & Employer > Product > Judgment > Management > Profession > Colleagues > Self.
Requirements Rules
• Functional: What system MUST do (inputs → outputs, reactions).
• Non-Functional (NFR): Constraints (security, performance, portability).
• Vague words to rewrite: Never use "instantaneously", "user-friendly", "little training" → Rewrite into measurable numbers (e.g. ≤ 200ms latency, ≤ 2 errors per 8 hrs).
• Use Case Relations:
  - «include»: mandatory sub-task; base is incomplete without it.
  - «extend»: optional branch at extension point; base is complete alone.
Kruchten 4+1 View Model
• Logical View: Classes, packages, domain objects. Audience: Devs & Users. Concern: Functionality.
• Process View: Concurrency, threads, runtime performance, scalability. Audience: Devs.
• Development View: Software code artifacts, modules, binaries, build hierarchy. Audience: Devs.
• Physical View: Hardware nodes, networks, servers. Audience: Operations.
• +1 Scenarios (Use Cases): Unifies and validates the other 4 views!
Architecture Patterns
• IEEE Definition: Fundamental organization of a system embodied in components, relationships, environment, and design principles.
• 3 Partitioning Steps: (1) System Structuring, (2) Control Modeling, (3) Modular Decomposition.
• 1. Layered Pattern: UI → Interface/Auth → Logic → DB.
  + Replaceable layers, defense-in-depth security.
  - Performance overhead across layers, hard clean separation.
• 2. Repository Pattern (IDE): Passive central DB + active tools.
  + Efficient sharing of large data, tool independence.
  - Single point of failure; data schema compromise.
• 3. Client-Server Pattern: Distributed servers offer services.
  + Failure in one server doesn't crash others; scalable.
  - Network latency, each service point of failure.
• 4. Pipe & Filter Pattern: Sequential data transforms.
  + Subsystem reuse, intuitive flow (Unix pipes).
  - Agreed data format overhead, high latency.
• MVC: Controller (input) → Model (data) → View (output).
Control Models
• Centralized - Call-Return: Top-down subroutine call tree for sequential systems (Main → Subsystems → Methods).
• Centralized - Manager Model: One central System Controller starts/stops/coordinates concurrent tasks (Sensors, Actuators, UI, Fault Handler).
• Event - Broadcast: Events published to bus; registered subsystems handle. Decentralized, but handling timing uncertain.
• Event - Interrupt-Driven: Hardware interrupt array mapped to memory addresses → handlers. Fast real-time, but hard to validate!
Testing Fundamentals & V-Model
• Verification: "Are we building the product RIGHT?" (conformance to specification).
• Validation: "Are we building the RIGHT product?" (satisfies user needs).
• Dijkstra's Axiom: "Testing shows the presence of bugs, NEVER their absence!"
• V-Model Pairs:
  - Requirements ↔ Acceptance Testing (Alpha/Beta)
  - System Spec ↔ System Testing
  - Architectural Design ↔ Subsystem / Integration Testing
  - Detailed Design ↔ Unit Testing
Test Scaffolding & JUnit
• Driver: Simulates the calling module (invokes unit).
• Stub / Mock: Simulates a called sub-module (dummy return).
• Harness: Test framework and runner (JUnit).
• Oracle: Mechanism comparing actual vs expected outputs.
• JUnit Lifecycle:
  @Test: Marks test method.
  @Before / @BeforeEach: Runs before EVERY test.
  @After / @AfterEach: Runs after EVERY test.
  @BeforeClass / @BeforeAll: Runs ONCE before test suite.
  @AfterClass / @AfterAll: Runs ONCE after suite.

  3. Security, Patient info manager, Report generation

SWE Exam 3 Study Notes • Side 2: UML Diagrams, Coverage & DB CSC 4350 / 6350 • Fall 2026
UML Class Diagrams Rules
• 3 Compartments: Always draw all 3 boxes: (1) Class Name, (2) Attributes, (3) Operations. Even if empty, draw the 3rd box line!
• Class Naming: Noun = Class, Noun Phrase = Attribute, Verb = Operation.
• Abstract Class: Italicized font or «abstract».
• Visibility: + Public | - Private | # Protected | ~ Package
• Attribute format: visibility name: type = default
• Operation format: visibility name(param: type): returnType
• Aggregation <>-- : Open diamond at whole. Weak ownership ("has-a"). Part outlives whole! E.g. Department <>-- Doctor (doctors retain licenses).
• Composition <*>-- : Solid diamond at whole. Strong ownership ("part-of"). Part destroyed with whole! E.g. Department <*>-- LabTest, Customer <*>-- Address.
• Generalization --|> : Hollow triangle at parent ("is-a"). E.g. MedicalRecord --|> SurgicalRecord.
• Realization ..|> : Dashed line with hollow triangle at interface. E.g. SavingsAccount ..|> InterestBearing.
• Dependency ..> : Dashed line with open arrow ("uses").
Adapter Pattern Class Diagram
• Client: Calls methods on the Target interface.
• Target: Interface expected by Client.
• Adapter: Implements Target (..|>) and wraps Adaptee via private reference (adapter.adaptee.specificRequest()).
• Adaptee: Existing class with incompatible interface.
Sequence Diagrams
• Lifeline: Vertical dashed line extending down from box.
• Activation: Vertical thin rectangle of execution control.
• Sync Call: Solid line + filled arrowhead ——▸ (sender blocks).
• Async Call: Solid line + stick open arrow ——> (non-blocking).
• Return: Dashed line + stick arrow <- - -
• Creation/Destruction: «create» points to box; X at bottom of lifeline destroys object.
• Fragments: alt (if-else separated by dashed line), opt (if only), loop [min, max], par (parallel).
Activity & Statechart UML
• Activity Diagram Elements:
  - Start Node: Solid black circle.
  - Activity State: Rounded rectangle.
  - Decision / Merge: Diamond with [guard].
  - Fork Bar: 1 incoming → 2+ concurrent parallel flows.
  - Join Bar: 2+ concurrent flows synchronized → 1 outgoing flow.
  - Activity Final: Bullseye (dot inside circle).
  - Swimlanes: Partitions showing responsible roles/actors.
• State Machine (Microwave Oven):
  - States: Waiting, Half power, Full power, Operation, Disabled.
  - Transition Syntax: Event [Guard] / Action
  Ex: start [door_closed] / run_generator(300W)
White-Box Structural Testing
• Statement Coverage ($C_0$):
  $\frac{\text{statements executed}}{\text{total statements}} \times 100\%$. Weakest metric! Fails to test untaken false branches in single if statements.
• Branch Coverage ($C_1$):
  Every decision edge (True & False) traversed at least once.
  Subsumption: Branch coverage subsumes Statement coverage!
• Condition Coverage: Each individual boolean condition in a composite expression evaluates to True and False at least once.
• MC/DC (Modified Condition/Decision):
  Avionics DO-178C standard. Each condition shown to independently affect decision outcome while holding others fixed.
  Test cases required: $n + 1$ (vs $2^n$ full condition).
• Path Coverage: Every execution path. Often infinite due to loops.
• Loop Boundary Coverage: 0 iterations, 1 iteration, typical, max-1, max iterations.
Black-Box (EP & BVA)
• Equivalence Partitioning (EP): Partition input into valid and invalid classes; pick 1 representative per class.
• Boundary Value Analysis (BVA): Test edges of ranges: $min-1, min, min+1, nom, max-1, max, max+1$.
• PIN [0000..9999]: Valid: 1234; Invalid: -1, 10000, "ABC", 3 digits, 5 digits.
5 Test Cases Template
Columns: [ID, Objective, Pre-Conditions, Steps/Inputs, Expected Result, Pass/Fail]
• TC-1 (Valid EP): Normal user registration → Saved to DB, HTTP 201 Created.
• TC-2 (Min Boundary): Input = 0 (min valid age) → Accepted as Infant.
• TC-3 (Negative BVA): Input = -1 → Error "Age must be ≥ 0", form rejected.
• TC-4 (Concurrency): Simultaneous withdrawals of $100 on $100 balance → 1st succeeds, 2nd rejected, balance never negative.
• TC-5 (Null/Exception): DoctorID = NULL → HTTP 400 Bad Request, graceful error logging (no 500 crash).
Relational Database & Normal Forms
• Entity Integrity: Primary Key (PK) cannot be NULL.
• Referential Integrity: Foreign Key (FK) must match existing PK in parent table or be NULL.
• 1NF: Atomic column values, no repeating groups.
• 2NF: 1NF + no partial functional dependencies (all non-key attributes fully depend on composite PK).
• 3NF: 2NF + no transitive dependencies (no non-key attribute depends on another non-key attribute).
"All attributes depend on the key, the whole key, and nothing but the key!"
